# Einbürgerungstest-Trainer – Build Plan

A small web app at **https://test.tsopany.com** for practising the official naturalisation
test catalogue. Google sign-in (open to any account), progress stored per user in Postgres.
Performance-based weighting shows weak questions more often than strong ones. It also has
a mock exam mode.

Stack is copied from the **board** app (`~/code/github/tsopany/board`); infrastructure lives in
`~/code/github/tsopany/tsopany-vm-setup`. This plan is self-contained.

## 2. Dataset (phase 1 – do this first, everything depends on it)

### 2.1 Sources

1. **Question texts + answer options + pictures:** the PDF above.
   The open-source repo **leben-in-deutschland/leben-in-deutschland-app** (MIT)
   has already extracted this exact PDF (same sha256) into
   `src/catalogue/data/bamf-catalogue.json` (460 questions; fields `num`, `part`,
   `state`, `stateCode`, `question`, `answers[4]`, `images`). Its extractor
   `src/catalogue/extract.mjs --pdf <path>` (Node 22, needs `pdfjs-dist` from
   `src/web`) also writes the pictures as `output/images/<num>-<n>.png`,
   with n = 1..4 left to right = "Bild 1".."Bild 4".
   → Use it: clone the repo, run extract on our PDF, keep `part == "general"` + `stateCode == "NW"`.
2. **Answer keys (preliminary):** the same repo, `src/web/data/question.json`
   (fields `question`, `a`–`d`, `solution` letter, `translation.en`). Match to
   the catalogue by **normalised question text + identical set of 4 answer texts**
   (normalise: NFC, `…`→`...`, typographic quotes → `"`, collapse whitespace,
   lowercase). Map the solution letter to the answer **text**, then to the
   index in the official answer order. Never trust the letter alone, because the
   repo's option order may differ from the PDF's.
   - A trial match already gave **286/310** keys. These **24 have no key yet**
     (mostly questions reworded in the 2025 catalogue):
     general `3, 5, 14, 17, 37, 41, 44, 58, 70, 82, 87, 108, 136, 140, 150, 199, 220, 249, 275, 276, 279, 299`, NRW `NW-9, NW-10`.
3. **Answer keys (authoritative, verifies all 310):** the official BAMF practice
   site `https://oet.bamf.de/ords/oetut/f?p=514:1` (Oracle APEX). Choose
   Bundesland **Nordrhein-Westfalen** on the start page, then the catalogue
   page (`f?p=514:30`) shows "Aufgabe N von 310". Each question page's HTML has
   HTML comments marking every option as `--> falsche Antwort =>` or
   `--> richtige Antwort =>`, followed by the option text. Navigation uses the
   select list `P30_ROWNUM` (1..310, page submit). Do it with a real browser
   session (Playwright, or the person's browser), ~310 page loads, with polite
   delays. Store the raw text of each page in `data/build/bamf_raw/` so it is
   never re-scraped.
   - Map BAMF "Aufgabe 1–300" to general 1–300 and "301–310" to NW-1–NW-10.
     Confirm by matching the question text, not only the position.
   - For picture questions the options read "Bild 1"…"Bild 4". Check against the
     picture order from the PDF.

### 2.2 Rules
- Final key = BAMF key. The repo key is only a cross-check.
- `verification.md` lists: count verified, any question where the repo key ≠ BAMF
  key, any text mismatch between PDF and BAMF site, and the 24 filled gaps.
- **Hard check:** 310 questions, exactly one key each, every key index 0–3, every
  picture question has its images present. The build script fails otherwise.
- The build script writes `shared/questions.json` and `client/public/images/*.png`.
  `data/questions_en.json` stays out of both.

### 2.3 `shared/questions.json` shape

```json
[
  {
    "id": "1",              // "1".."300", "NW-1".."NW-10"
    "part": "general",      // or "state"
    "text": "In Deutschland dürfen Menschen offen etwas gegen die Regierung sagen, weil …",
    "options": ["hier Religionsfreiheit gilt.", "die Menschen Steuern zahlen.",
                "die Menschen das Wahlrecht haben.", "hier Meinungsfreiheit gilt."],
    "correct": 3,           // index into options, official order
    "images": []            // e.g. ["21-1.png","21-2.png","21-3.png","21-4.png"] or a single context picture
  }
]
```

Both api (validates ids, computes `correct` server-side) and client (renders) import it
through `shared/`. Picture questions in our 310 (13): `21, 55, 70, 130, 176, 181, 187, 209, 216, 226, 235, NW-1, NW-8`.
Some have 4 option pictures ("Bild 1–4"), others have one picture plus text options.
Render accordingly.

`questions_en.json`: `{ id, text, options[4] }` from the repo's `translation.en`
where available. Gaps are fine (for us only).

## 3. Question selection (the core logic)

Lives in `shared/` as pure, unit-tested functions: `(answers, meta, now, rng) → question id`.
The client fetches the user's answers and calls them; the api never picks.

All state is **derived from the `answers` rows** (see §4), so the rules can change later
without losing history.

### Per-question derived state
- `attempts`, `correct_count`, `last_answered_at`, `last_result`
- `box` (Leitner 0–4): wrong → 0; correct → box+1 (max 4). Unseen = no box.
- `mastered` = box 4 (4 correct in a row)

### Phase A – Coverage (until all 310 have ≥ 1 answer)
- On first use, shuffle the 310 ids once with a stored seed into a **deck**.
- Each pick:
  - With probability **1/3**, if the **review pile** is non-empty, take from the
    review pile: questions whose `last_result == wrong`, oldest first, and only if
    answered wrong ≥ 2 h ago so it isn't asked again right away.
  - Otherwise take the **next unseen** card from the deck (no repeats).
  - If the deck is exhausted, switch to Phase B.
- A question leaves the review pile when answered correctly.

### Phase B – Weighted
- Weight by box: unseen/0 → **16** (unseen only occurs when "Schwache Fragen üben" runs during Phase A), 1 → **8**, 2 → **4**, 3 → **2**, 4 (mastered) → **0.5**.
- Cool-down: weight × 0.1 if the question was answered in the last 24 h. Never pick
  any of the last 10 picked questions.
- Weighted random pick.

### Shared
- The same picker serves "Üben" / "Nächste Frage" and the
  "Schwache Fragen üben" mode (that mode uses Phase B weights regardless of phase).
- Mock exam answers also feed the boxes (§5).

## 4. Database and api

Postgres 17, MikroORM entities in `api/src/db/entities/`, numbered SQL migrations in
`api/src/db/migrations/` (immutable once applied). Keep board's `users`, `identities`,
`refresh_tokens`; drop everything else.

```sql
-- users, identities, refresh_tokens: as in board (Google only)

CREATE TABLE answers (
  id            BIGSERIAL PRIMARY KEY,
  user_id       UUID    NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  question_id   TEXT    NOT NULL,              -- "1".."300", "NW-1".."NW-10"
  chosen        SMALLINT NOT NULL CHECK (chosen BETWEEN 0 AND 3),
  correct       BOOLEAN NOT NULL,              -- computed by the api from shared/questions.json
  answered_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  source        TEXT    NOT NULL,              -- 'practice' | 'weak' | 'exam'
  exam_id       BIGINT  REFERENCES exams(id)
);
CREATE INDEX idx_answers_user_q ON answers(user_id, question_id, answered_at);

CREATE TABLE exams (
  id           BIGSERIAL PRIMARY KEY,
  user_id      UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  started_at   TIMESTAMPTZ NOT NULL,
  finished_at  TIMESTAMPTZ,
  score        SMALLINT,                       -- 0..33
  passed       BOOLEAN                         -- score >= 17
);

CREATE TABLE user_meta (
  user_id  UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  key      TEXT NOT NULL,                      -- 'seed' only: deck position and last picks are derived from answers
  value    JSONB NOT NULL,
  PRIMARY KEY (user_id, key)
);
```

Routes (all under `/api`, all authenticated except auth and health):
`GET /health`, Google auth routes (as board), `GET /me`, `GET /answers`, `POST /answers`,
`POST /exams`, `POST /exams/:id/finish` (final answers + score), `GET /exams`,
`GET /seed`, `DELETE /progress` (reset, confirmed in the UI), `DELETE /me` (delete account).
Keep board's rate limits, request guard, security headers, redaction plugins.
Account deletion (board has `deleteAccount`) stays: it is the user's data.

## 5. Screens (German UI, vue-i18n with `de` only)

1. **Frage** (quiz screen)
   - Question text (large), picture(s) if any, 4 answer buttons.
   - After tapping: lock buttons, chosen = red/green, correct always shown green,
     short "Richtig!" / "Leider falsch".
   - Buttons: **Nächste Frage**, **Zur Übersicht**.
   - Small header: "Frage 128 · gesehen 212/310".
2. **Übersicht** (home + stats)
   - Phase indicator: "Phase 1: 212/310 Fragen gesehen" / "Phase 2: gezieltes Üben".
   - Counts: gemeistert / in Arbeit / ungesehen (+ simple bar).
   - Trefferquote: overall and last 7 days.
   - **Prüfungsreife:** estimated pass probability. Monte Carlo of 10,000 simulated exams
     (30 random general + 3 random NRW), per-question p = (correct+1)/(attempts+2),
     unseen p = 0.25 (guessing). Show "Bestehenswahrscheinlichkeit ~84 %" and the expected score.
   - **Schwächste 10 Fragen** (lowest box, then highest error rate). Click → practice that question.
   - Buttons: **Üben**, **Schwache Fragen üben**, **Probeprüfung**, **Einstellungen**.
3. **Probeprüfung** (mock exam)
   - 33 questions: 30 random general + 3 random NRW, shuffled. 60:00 countdown.
   - No feedback during the exam. She can move back and forth and change answers. "Abgeben" button.
   - At time-out, auto-submit.
   - Result: score /33, BESTANDEN (≥ 17) / NICHT BESTANDEN, list of wrong
     questions with the correct answer. History of past exams on the Übersicht.
   - Only the final answer per question is written to `answers` (source `exam`).
4. **Anmelden** – Google button. **Einstellungen** – "Fortschritt zurücksetzen" (confirm dialog),
   "Konto löschen", logout. **Impressum/Datenschutz** page (board's `Legal.vue`, adapted: Google
   login, data stored in Postgres on the VM).
